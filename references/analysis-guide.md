# 分析方法指南

## 0. 分析对象与依据优先级

- 分析对象是基准 A、B 两个快照的**净差异**（`git diff A B`），即区间内全部提交的最终叠加效果；不是逐个提交分析，更不是只看 A、B 两个提交各自的改动。
- 一切功能点、变更类型、影响与风险判断必须以 diff 代码内容为依据（哪个文件、哪个函数/逻辑、行为怎么变）；commit message 和提交数只用于提交人归属与变更概览，与 diff 冲突时一律以 diff 为准。
- 净差异中不存在的东西不写入报告：中途引入又被撤销的改动在快照差里看不到，对测试而言就等于没改。

## 1. 模块归类

- 默认按变更文件路径的前 1–2 级目录分组（如 `apps/web/src/pages/`、`server/src/services/`）。
- 目录名与业务语义对不上时，读仓库 README、package.json/pom.xml 等入口配置确认结构，按功能域归组（如"设置页"、"知识库"、"用户认证"）。
- 报告中的模块名用业务可读名并附代表目录，例如：`设置页（apps/web/src/pages/Settings.jsx）`。
- 散落的杂项文件（根目录配置、脚本）归入"工程配置"一个模块，不要让模块列表碎片化。

## 2. 变更类型判定

类型取值：新功能 / 缺陷修复 / 重构 / 性能优化 / 配置变更 / 依赖升级 / 文档 / 测试代码 / 样式调整 / 其他。

判定一律依据 diff 代码实质（改了什么逻辑、接口、资源）；commit message 只作辅助线索，与 diff 冲突时以 diff 为准。净差异中相邻或重叠的改动合并为同一功能点描述，不逐 commit 罗列。

## 3. 风险分级标准

评级对象是"模块 × 变更"，不是单个文件。拿不准时宁可比调高一级，并在理由里写明不确定性。

**高风险**：
- 核心业务逻辑、计费、鉴权、数据写入路径的改动
- 公共组件/工具函数/基类/接口契约（参数、返回值、错误码）变化——影响所有调用方
- 数据结构、DB schema、存储格式变更或数据迁移
- 并发、事务、缓存失效相关逻辑
- 安全相关：加密、权限校验、输入校验的修改或放宽
- 大面积删除/重命名（可能破坏外部引用）

**中风险**：
- 业务模块内的缺陷修复（修复本身可能引入新问题）
- 默认值/常量/开关背后的行为变化
- 依赖升级（patch 偏低，minor 中，major 偏高）
- UI 交互流程、页面结构变化（影响 e2e 和手工用例步骤）

**低风险**：
- 文档、注释、日志文案
- 测试代码、CI 脚本
- 不影响布局结构的纯样式微调

每条风险必须附依据，格式：`风险原因（证据：路径/文件.ext 中 <函数/逻辑> 的 <具体变化>）`；commit hash 仅作辅助定位，不能单独作为依据。

## 4. 影响范围判定

分三层，逐层给出：

1. **直接影响**：A..B 中被改文件对应的功能本身。
2. **间接影响（调用方）**：grep 被改的导出符号（函数名/类名/组件名/API 路由/配置键/env 变量名），列出引用文件，归入受影响模块。这是"重点测试模块"的主要来源。
3. **运行时/数据影响**：接口契约变化的消费者、数据格式变化的下游、前端调用的后端路由变更影响的页面。这一层通常无法完全用 grep 证实，未证实的标【推断】。

## 5. 用例集分析

### 5.1 加载

- 运行目录 `.test-risk.json` 中对应仓库条目的 `repos[].testcases` 数组逐个读；`path` 相对该仓根；xlsx 可选 `sheet` 字段（null 或缺省 = 全部 sheet）。
- 表头列语义识别（各家用例模板列名不同）：用例编号/ID、所属模块/功能/产品、标题/用例名称、前置条件、操作步骤、预期结果、优先级。
- xlsx 读取顺序：python + openpyxl（示例如下）→ 会话内的 xlsx 表格技能 → 请用户导出 CSV。Windows 下 `python --version` 无输出多半是 WindowsApps 存根，直接视为 python 不可用。openpyxl 示例：

```bash
python -c "
import openpyxl
wb = openpyxl.load_workbook('用例.xlsx', read_only=True, data_only=True)
for ws in wb.worksheets:
    for row in ws.iter_rows(values_only=True):
        print('|'.join('' if c is None else str(c) for c in row))
"
```

### 5.2 匹配与三分类

对每个变更功能点，在用例集中查找相关用例：
- 匹配依据（按优先级）：用例的"所属模块/功能"字段命中变更模块名/目录名/路由/页面名；标题与功能点语义相关；步骤中引用了被改的接口/按钮/入口。
- 三分类：
  - **重点回归用例**：现有用例覆盖了变更功能 → 列编号+标题+对应变更点+回归原因（对应哪条风险）。
  - **需更新用例**：变更改变了行为/接口/文案，用例的步骤或预期结果可能已过时 → 列编号+过时原因（指向具体 commit）。
  - **需补充用例**：变更功能点在用例集中无任何覆盖 → 给出建议用例（标题、步骤要点、预期结果、建议优先级＝对应风险等级）。完全无用例的变更模块也要在这里体现。
- 匹配是语义判断，拿不准的标"疑似相关，建议人工确认"，不要硬归档。

## 6. 大 diff 抽样策略

- 触发条件：`--stat` 总计 > 3000 行，或单文件 > 800 行。
- 每模块抽 2–3 个核心文件读完整 diff；优先级：业务逻辑/接口/公共模块 > 页面/组件 > 样式/资源/文档。
- 批量机械改动（rename、格式化、批量替换）只看 name-status + 抽 1 个样本确认性质。
- 报告附注必须写"大变更，基于抽样分析，非逐行全量"。

## 7. 多仓汇总

- 整体风险等级取各仓最高；结论摘要按"全局一句 + 每仓一句"组织。
- 跨仓影响判定：某仓变更了对外契约（API 路由、导出函数、事件名、共享数据格式、共享包版本）时，在其余分析仓里 grep 该契约符号——命中文件即跨仓影响证据，写入对方仓的影响范围并注明契约来源仓；无法 grep 证实的跨仓判断标【推断】。
- 各仓用例集独立分析、互不混用；某仓未配置用例集只影响该仓自己的章节。
